# Build a lean, replaceable OpenBB research stack

**Build the workflow around a pinned local OpenBB install (`openbb` 5.0.0) exposed to Claude through `openbb-mcp-server`, add free official-data connectors (SEC EDGAR, FRED), cherry-pick a handful of existing finance skills, and write five custom skills for the parts nobody has built.** The notes found no ready-made skill that combines OpenBB data, long-only screening, dashboards and thesis tracking, so that gap is yours to fill. Treat OpenBB as replaceable: the company announced a wind-down in August 2026, and the license of the current wheel is contradicted across sources. Your existing dashboard skills (data:build-dashboard, dataviz, data:validate-data) already cover the front end, so the new work is finance logic and validation discipline. On the ML side, the evidence supports modest expectations: published factor premia decay roughly 25-50%, many fail under value-weighted tests, and hobbyist-scale multiple testing is exactly where backtests mislead. Build screens and diagnostics first, ML later, and judge every model against equal-weight and single-factor baselines after costs. This is educational research, not personalized investment advice. Several provider-level facts are unverified and flagged below.

## OpenBB is a good data hub with an unstable parent

OpenBB's Open Data Platform (the `openbb` package, now V5) is described as a "connect once, consume everywhere" layer serving Python, a REST API, Workspace, Excel and MCP servers ([OpenBB blog](https://www.openbb.co/blog/openbb-releases-open-data-platform)). PyPI shows `openbb` **5.0.0 released 29 Sep 2026**, Python >=3.10, installed as extensions (for example `pip install openbb-equity openbb-cboe`), with `openbb-build` required after adding or removing extensions ([PyPI](https://pypi.org/project/openbb/)). The V5 extension index lists mostly official and macro sources: Sec, Fred, Ecb, Imf, Oecd, Bls, Nasdaq, Cboe, Finra, Famafrench, Technical, Quantitative and Econometrics ([docs reference](https://docs.openbb.co/odp/python/reference)). The notes could not confirm whether the old commercial and unofficial providers (yfinance, FMP, Polygon, Intrinio, Tiingo) still ship in V5, so check this before designing around them.

The MCP side is the strongest integration point. `openbb-mcp-server` (v2.0.0 on 28 Sep 2026, PyPI-labelled Apache-2.0) generates tools from whatever extensions you install and runs over stdio for Claude Desktop via `uvx`, or over HTTP at `127.0.0.1:8001/mcp` ([MCP quickstart](https://docs.openbb.co/odp/python/quickstart/mcp)). Because tool counts can balloon, use `--allowed-categories` or `--tool-discovery`, which hides tools behind search and call wrappers. Version 2 also adds `run_pipeline`, Plotly-to-Workspace artifacts, bearer auth and five bundled skills ([extension docs](https://docs.openbb.co/odp/python/extensions/interface/openbb-mcp)). One security note from the notes: `install_skill` writes a SKILL.md to the server's disk, so leave it off or keep the server bound to localhost.

Data quality is the weakest verified area. The notes confirm only that some providers need keys stored in `~/.openbb_platform/user_settings.json` and that OpenBB chose not to be a data vendor ([OpenBB blog](https://openbb.co/blog/openbb-belongs-to-everyone/)). Per-provider pricing, free-tier limits and Nordic coverage were **not verified**. The notes' working hypotheses, explicitly from prior knowledge rather than sources, are that yfinance is free but unofficial and carries Helsinki, Stockholm, Copenhagen and Oslo tickers, and that SEC, FRED and ECB are free and official. Test these yourself on a few Nasdaq Helsinki names before committing.

## Five custom skills fill the real gap

The notes' gap analysis concludes that existing skills are dividend- and FMP-bound, institution-oriented with paid connectors, or crypto-first, and none combines OpenBB data, long-only screening, dashboard output and thesis tracking ([Anthropic](https://github.com/anthropics/financial-services-plugins), [tradermonty](https://github.com/tradermonty/claude-trading-skills), [agiprolabs](https://github.com/agiprolabs/claude-trading-skills)). The skills below are the notes' inferences, ordered by what I would build first.

1. **openbb-data-pull** sets fetch, caching and validation conventions: provider fallbacks, adjusted prices, EUR conversion, and data-quality checks. Everything else depends on it, and it is where you absorb V5 provider uncertainty.
2. **buy-candidate-screener** runs a configurable factor screen (valuation, quality, balance sheet, growth, dividend safety, momentum filter) and returns a ranked table with explicit criteria and a "why flagged" column. Word the output as screen results, never as buy or sell instructions.
3. **portfolio-dashboard** shows holdings, allocation, drawdown, benchmark comparison and dividends, built on data:build-dashboard and dataviz conventions, with data:validate-data as the last step.
4. **thesis-and-watchlist-tracker** adapts Anthropic's thesis-tracker and catalyst-calendar so each candidate carries a written thesis, falsifiers and review dates.
5. **backtest-hygiene** encodes the validation checklist from the methods notes (below) for long-only rebalancing backtests, adapting the walk-forward ideas in agiprolabs. A sixth, Finland-specific skill (Helsinki tickers, euro handling, osakesäästötili notes) is only an idea; the notes researched no sources for it.

Define your actual screening criteria and providers first. The notes state that the skills should be scoped only after that decision.

## ML directions: start simple, defend against overfitting

The factor literature gives two honest readings. Hou, Xue and Zhang find **65% of 452 anomalies fail a |t|>=1.96 hurdle** under NYSE breakpoints and value weighting, and 96% of trading-friction anomalies fail ([RFS 2020](https://ideas.repec.org/a/oup/rfinst/v33y2020i5p2019-2133..html)). McLean and Pontiff report about a **26% return drop within three years** after a sample ends, and Chen and Zimmermann put decay near 25% at year 3 and 40% at year 5 ([arXiv](https://arxiv.org/pdf/2209.13623), [McLean-Pontiff](https://ivey.uwo.ca/media/3775549/pontiff.pdf)). The same Chen-Zimmermann paper argues almost all findings replicate, with publication bias explaining only 10-15% of in-sample returns. The difference is largely equal-weighted, microcap-inclusive versus value-weighted tests. For you the practical rule is to evaluate screens on a large-cap, value-weighted universe, and the notes suggest haircutting published returns by roughly half (an inference, not a sourced figure).

For ML proper, Gu, Kelly and Xiu find trees and neural nets beat other methods, with momentum, liquidity and volatility the dominant signals ([NBER w25398](https://www.nber.org/papers/w25398)). Their setting is a huge CRSP universe including small caps, so the result does not transfer automatically to a hobbyist large-cap universe; the notes did not verify follow-up work on post-cost profits. A sensible path is ridge or a shallow gradient-boosted model on a few cross-sectionally ranked features, with forward excess-return rank as target. For portfolio construction, skfolio is scikit-learn-compatible and offers walk-forward and Combinatorial Purged CV, regularised MeanRisk (variance, CVaR, CDaR), HRP and NCO, under a BSD-3 license ([paper](https://arxiv.org/pdf/2507.04176), [CPCV docs](https://skfolio.org/generated/skfolio.model_selection.CombinatorialPurgedCV.html)). Against your background this is a comfortable fit: compare ridge-Markowitz, HRP, inverse-volatility and 1/N, and trust an optimizer only if it beats the simple ones net of costs.

For LLM features, Glasserman and Lin show lookahead bias matters mainly in-sample and that anonymising company names improved performance ([arXiv 2309.17322](https://arxiv.org/abs/2309.17322)); ChronoBERT-style models trained only on text available at each date suggest the bias is modest in one news application ([arXiv 2502.21206](https://arxiv.org/abs/2502.21206)). The safe use is structured extraction (risk factors, guidance changes) from filings after the model's cutoff, with quoted spans checked against source text and forward paper-tracking rather than a backtested alpha claim. The notes found no verified evidence on earnings-call alpha, post-cost value or hallucination rates. Reinforcement learning (FinRL) and HMM regime models gathered no supporting evidence; the notes call RL hype-prone and regime models fragile. Use regime tools such as the breadth and uptrend skills as descriptive context, not as trading triggers.

## Roadmap, from data layer to forward test

Start in a pinned virtual environment with `openbb==5.0.0` and only the extensions you need (SEC, FRED, ECB, and whichever equity-price provider survives your check), then run `openbb-build`. In week one, connect `openbb-mcp` to Claude Desktop over stdio with category restrictions, add the EDGAR and FRED servers, and write openbb-data-pull; verify prices and fundamentals for five US and five Helsinki tickers against a second source, because the notes could not verify Nordic coverage. In weeks two and three, build the screener and portfolio-dashboard on your existing dashboard skills, taking the logic from tradermonty's value and quality screeners and Anthropic's comps and DCF workflows. In week four, add the thesis tracker and a small watchlist. Only then start ML: build the baseline factor composite, then ridge or shallow GBM, then portfolio construction in skfolio, each judged against equal-weight, an index and a single-factor benchmark.

Run every research step through the notes' eight-point checklist: point-in-time fundamentals with reporting lags of at least three to four months (free-tier fundamentals are restated and not point-in-time, and yfinance prices are survivor-biased, per the notes' inference); a size and liquidity filter to exclude microcaps; time-ordered splits with purge and embargo equal to the label horizon; logging every trial and computing the Deflated Sharpe Ratio and Probability of Backtest Overfitting ([Bailey and Lopez de Prado](https://papers.ssrn.com/abstract=2460551), [Bailey et al.](https://papers.ssrn.com/abstract=2326253)); costs and turnover sensitivity; benchmark comparison; a final untouched forward or paper period; and anonymised, post-cutoff text only for LLM features. The last step is the one that matters most: hold-out samples alone are unreliable against backtest overfitting, so a genuine forward period is your only clean test. Keep the dashboard local (Streamlit/Plotly or the HTML skills) rather than depending on hosted Workspace, a choice the notes infer is lower-risk for durability.

## Caveats you should weigh before relying on this

**OpenBB's future is uncertain.** OpenBB announced a company wind-down on 25 Aug 2026 and said it would release Workspace, Copilot, Excel Add-in and ODP under a permissive license; OpenBQ, a non-profit, stewards the technology and FINOS is proposed to steward Workspace, with release timing "to be shared later" ([OpenBB](https://openbb.co/blog/openbb-belongs-to-everyone/), [FINOS #445](https://github.com/finos/community/issues/445)). **The license is contradictory:** the `openbq-org/OpenBB` README says Apache 2.0, while the October 2025 blog and a raw LICENSE from the old repo say AGPL-3.0 ([GitHub](https://github.com/openbq-org/OpenBB), [LICENSE](https://raw.githubusercontent.com/OpenBB-finance/OpenBB/develop/LICENSE)); the AGPL file may be stale. A search snippet of an X post claims everything was open-sourced under Apache, but the page was blocked and its date is unverified. For personal local use either license is workable (AGPL bites only if you offer a modified version as a service), but the definitive license of the 5.0.0 wheel is unconfirmed. The hosted Workspace Community tier is free for individuals but excludes export, sharing and the Excel add-in and collects usage analytics, and its continuation is unconfirmed ([pricing](https://openbb.co/pricing)).

**Unverified items and gaps from the notes.** Per-provider pricing, limits and Nordic coverage; whether yfinance, FMP and Polygon extensions exist in V5; exact tool lists per equity route; Workspace self-hosting; free-tier limits for Alpha Vantage and Massive; Financial Datasets pricing; repo maintenance recency; whether Anthropic's plugin install works on your individual plan; and any hands-on or end-to-end test. In the methods notes, the Piotroski, Magic Formula, QMJ, momentum-crash, low-volatility, DeMiguel 1/N, HRP and HMM evidence, GKX out-of-sample R-squared, and any figure for hobbyist-achievable net alpha or transaction costs were not retrieved and are deliberately not asserted here. Aggregator marketplaces and unvetted yfinance or findata MCP servers are secondary or unverified.

**Overfitting is the main personal risk.** A student iterating on features, thresholds and hyperparameters is the textbook multiple-testing case, and a long-only constraint helps with shrinkage but does not remove selection bias. Cap positions, rebalance infrequently, and treat any backtest that beats a cheap index before costs as a hypothesis. Note also that data from Yahoo-derived sources is, in the notes' unverified inference, ToS-grey beyond personal use.

**This is educational research, not personalized investment advice.** Nothing here is a recommendation to buy or sell any security, and the notes' own sources (Anthropic's repo, tradermonty) carry the same education-only disclaimers. Tax and account-structure questions for Finland were not researched.

## Conclusion

The notes point to an unglamorous conclusion: the leverage in this project is in data hygiene and validation, not in model sophistication. The MCP plumbing exists and is free; what is missing is a skill layer that forces point-in-time data, universe filters, trial logging and baseline comparison onto every screen you build. That makes backtest-hygiene and openbb-data-pull, not the ML model, the highest-value custom work, and it makes your realistic target a documented, low-turnover large-cap screening process rather than an alpha engine.

The wind-down changes how you should build rather than whether. Pin versions, keep adapters thin, store raw pulls locally, and keep the dashboard independent of hosted Workspace, so that swapping OpenBB for direct EDGAR, FRED and another price source costs days rather than a rewrite. Revisit the license and release-timeline questions once OpenBQ or FINOS publish more, and run the Helsinki-ticker data check before investing any further effort.
